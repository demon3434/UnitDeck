# ADR 0001: UnitDeck - 通用进程与 AI 显存/系统资源管理控制台架构决策

## 状态 (Status)
**已接受 (Accepted)** - 2026-11-07

---

## 决策背景 (Context)
用户在 Debian 主机（Headless，无显示器）上部署了多个 AI 程序和应用服务，由 systemd 进行管理。主机显卡为 12GB 显存，受物理显存限制多个重量级程序不能并发运行。同时，用户希望将该工具打造为一个**高通用性、安全可控、开箱即用的进程与服务管理平台**，能够兼顾启停控制、开机自启设置、资源清理、精美视觉以及 Docker 容器化交付。

用户明确提出了以下边界要求与核心诉求：
1. **通用进程管控**：不局限于单一主机的 AI，可作为通用的 systemd 进程管理工具，支持启停（Start/Stop/Restart）与**设置开机自启动（Enable/Disable）**。
2. **防呆确认**：**所有启停与自启操作必须有弹窗二次确认**，防止误触。
3. **纳管流程**：用户必须先进入设置菜单，从系统服务中选取想要管理的程序，主页面只呈现和操作这些程序。
4. **一键全停与清理**：
   - 停止范围**不需要做额外的兜底校验**，完全以用户纳管名单为准；
   - **超时强制杀进程**：在设置中提供配置开关，勾选后超时未退出自动调用 `systemctl kill` 强制杀掉；
   - **多维度资源清理（显存 + 内存 + CPU）**：在设置中提供开关，按需清理脱离服务的孤儿/残留进程，彻底腾出显存、内存与 CPU。
5. **服务范围与过滤机制**：
   - 权限覆盖：同时支持**系统级（root）**与**普通用户级（`systemctl --user`）**服务；
   - 傻瓜式服务过滤：通过路径与特征**自动排除系统底层核心 service**（如 systemd 底层组件），重点展示位于 `/etc/systemd/system/`、`/usr/local/lib/systemd/system/` 及用户级目录中的用户程序；
   - 兜底配置：若自动扫描无法满足，在图形化界面中提供**手动添加自定义程序**的输入表单（配置任务名称、服务名或启停脚本），持久化存储。
6. **安全与网络**：
   - 访问鉴权：**必须设置用户名密码**（支持设置初始账号密码与修改，拦截未经授权的访问）；
   - 网络定位：纯内网运行，默认开箱即用端口（如 `8080`）。
7. **界面与 DaisyUI 呈现**：
   - 在设置菜单中提供**多款丰富 DaisyUI 主题自由切换**（带色板预览，展现 DaisyUI 丰富视觉风格）；
   - **完全适配手机/移动端**触控浏览与快捷操作；
   - **单个代码文件严格不超过 500 行**，前端使用 **Vue 3 + TypeScript**，严禁纯 JavaScript。

---

## 架构决策与方案 (Decisions)

### 决策点 1：通用进程控制与全局二次确认机制 (All-Action Modal Confirmation)
- **技术决策**：
  1. 支持对每个受控单元执行四类控制动作：`start` (启动)、`stop` (停止)、`restart` (重启)、`enable` (开启自启)、`disable` (关闭自启)；
  2. **强制二次确认机制**：前端封装统一的全局确认模态框组件 `ConfirmModal.vue`，任何对服务的“启动”、“停止”、“重启”、“设置自启”以及“一键全停”操作，均必须弹出包含目标服务名、影响说明与高危动作色标的模态框，用户点击确认后才触发后端 API；
  3. 状态联动：操作触发后，按钮进入 Loading 态，并由状态轮询器确保状态变更完成后刷新界面。

#### 【用户补充细节】专栏
> - **用户原话**：“我希望做成一个通用性的程序，不仅针对我这台12GB显存的主机，我希望做成一个管理这些进程的工具，可以启停、设置是否开机自启动。所有操作都要有弹窗确认。用户先进入设置菜单，选取哪些程序纳入本web页面的管理，然后只能操作这些程序。”
> - **边界与特例逻辑**：
>   - 绝不仅限于 AI 程序，任何在主机上的通用进程/应用只要注册为 systemd 均可管理；
>   - 杜绝一切“单点即生效”的危险交互，所有操作均必须有弹窗确认；
>   - 主控制台与设置菜单严格解耦：主面板“只读 + 仅操作已纳管名单”，纳管增删与范围定义必须在设置菜单中完成。

---

### 决策点 2：一键全停范围与“超时强杀 + 显存/内存/CPU清理”三级配置
- **技术决策**：
  1. **全停范围**：后端在执行一键全停时，只针对用户当前已开启纳管名单中的全部 active 服务，不执行额外的白名单限制，完全信任用户的自主勾选；
  2. **超时强制杀死机制 (Timeout & Force Kill)**：
     - 在系统设置中增加配置项：`enable_force_kill`（是否启用超时强杀，默认可选）与 `kill_timeout_seconds`（超时秒数，如 8 秒）；
     - 当服务在规定超时后仍处于 `deactivating` 或仍有主 PID 存活时，系统自动调用 `systemctl kill -s SIGKILL <unit>` 强制终止；
  3. **幽灵资源多维清理引擎 (Ghost Resource Sweeper: GPU + RAM + CPU)**：
     - 在系统设置中提供开关：`enable_ghost_cleaning`；
     - 当用户触发一键全停或点击【深度清理资源】时，系统不仅停止 service，还会：
       - **显存清理**：扫描 `nvidia-smi` compute-apps 中脱离已停止服务的残留 Python/CUDA 僵尸进程并释放；
       - **内存与 CPU 清理**：检测处于 defunct/zombie 或 CPU 占用异常的关联子进程，执行清理，彻底恢复宿主机纯净状态。

#### 【用户补充细节】专栏
> - **用户原话**：“Q2.1 停止范围：不需要做额外的兜底校验。Q2.2 超时与强制清理：需要在设置菜单中配置选项，勾选之后，超时未退出则自动调用 `systemctl kill` 强制杀掉。Q2.3 幽灵显存清理：按需清理，这个开关也要在设置菜单中配置，除了显存，内存、CPU也要清理。”
> - **边界与特例逻辑**：
>   - “超时强杀”与“幽灵资源清理”必须做成**设置菜单里的独立可配置项**，让用户按需开启，并在执行一键全停时联动生效；
>   - 清理范围明确覆盖三大物理硬件资源：显存（VRAM）、系统内存（RAM）和处理器（CPU）。

### 决策点 3：双层 systemd 智能过滤（系统服务排除）与自定义程序兜底
- **技术决策**：
  1. **覆盖范围**：通过后端同时探测系统级服务（`/etc/systemd/system/`, `/usr/lib/systemd/system/`）与普通用户级服务（`~/.config/systemd/user/` 及 `systemctl --user`）；
  2. **智能排除算法（排除系统核心服务，保留用户程序）**：
     - 规则过滤：自动过滤掉匹配系统基础架构黑名单的 unit（如 `systemd-*.service`, `sys-*.service`, `dbus*.service`, `getty@*.service`, `udev*.service`, `apparmor.service`, `auditd.service`, `cron.service`, `polkit.service`, `rsyslog.service`, `ssh*.service` 等）；
     - 路径优先算法：优先展示存放在 `/etc/systemd/system/`（用户自建服务默认安装目录）和 `systemctl --user` 的服务；
     - 搜索与分类：提供实时输入过滤，同时提供一键“仅看用户自建服务”筛选器；
  3. **图形化自定义程序兜底方案 (Manual Config Fallback)**：
     - 在设置页提供【手动添加受控程序】功能；
     - 允许用户直接在 UI 上输入：程序名称、显示别名、关联的 systemd unit 名（或自定义启停命令脚本），持久化写入配置文件；
     - 保证“傻瓜式一键勾选”为主，“图形化自定义配置”为辅，100% 覆盖任何边缘环境。

#### 【用户补充细节】专栏
> - **用户原话**：“Q3.1 服务的范围与权限：这个我还真不了解，到底是root还是普通用户，我希望是都能纳入管理，我希望本程序是通过docker运行，目录映射，管理systemd的软件。Q3.2 发现与展示逻辑：我希望排除系统自己的service，只列出用户自己的程序。但我不知道怎么实现这个筛选。如果实在不行，就让用户自己配置了……最好还是能实现让用户自己选择，这样操作傻瓜。”
> - **边界与特例逻辑**：
>   - 必须兼顾 root 系统服务与普通用户服务；
>   - 核心难点是“系统服务太多，用户眼花”，系统必须有内置的排除过滤规则，让列表一打开就是干干净净的用户自装软件；
>   - 同时保留兜底的自定义添加表单，满足任何特殊服务需求。

### 决策点 4：内置安全认证 (Authentication) 与无头部署模型
- **技术决策**：
  1. **认证机制**：
     - 后端实现基于 JWT Token / Session 的轻量登录拦截中间件；
     - 提供独立登录页面 `LoginView.vue`，所有 API 请求需携带 Token；
     - 初始运行默认生成或配置管理员账号（如默认 `admin / unitdeck123`，支持在 Web 设置中直接修改密码）；
     - 凭据存储在持久化配置 `data/auth.json` 中；
  2. **网络模式**：
     - 默认暴露端口为 `8080`（支持通过环境变量 `PORT` 自定义）；
     - 面向纯内网 / LAN / VPN 环境设计，开箱即用。

#### 【用户补充细节】专栏
> - **用户原话**：“Q4.1 访问鉴权：需要设置用户名密码。Q4.2 默认端口与反向代理，我没有端口偏好，这么重要的管理工具，也不会反代到公网。”
> - **边界与特例逻辑**：
>   - 必须有用户密码登录页面，防止局域网内其他人通过 IP 误入并执行全停；
>   - 默认端口 `8080`，安全可靠。

---

### 决策点 5：丰富 DaisyUI 多主题画廊与手机移动端全响应式设计
- **技术决策**：
  1. **DaisyUI 丰富主题画廊 (Theme Gallery)**：
     - 在设置菜单中提供可视化的【主题展示与切换面板】，内置展示 DaisyUI 超过 20+ 款精美主题（如 `night`, `dim`, `dark`, `synthwave`, `cyberpunk`, `dracula`, `forest`, `luxury`, `nord`, `retro`, `coffee`, `winter` 等）；
     - 每个主题均展示其原生的主色、副色、强调色、背景色调色盘缩略图，用户点击即时全局预览并持久化到本地存储；
  2. **手机/移动端适配**：
     - 采用 Tailwind 响应式断点（`sm`, `md`, `lg`）；
     - 移动端下顶栏收缩为紧凑型状态栏（GPU 显存进度条、一键全停按钮适配拇指大触控区）；
     - 服务卡片在手机端呈现流畅的单列自适应布局，弹窗二次确认全屏贴底优化；
  3. **代码工程与行数控制**：
     - 前端采用 **Vite + Vue 3 (Composition API / `<script setup>`) + TypeScript + Tailwind CSS + DaisyUI**；
     - 严格遵守**单个代码文件绝不超过 500 行**，每个组件保持职责单一、体积紧凑。

#### 【用户补充细节】专栏
> - **用户原话**：“Q5.1 主题风格：在设置菜单页面中，用户自由切换。主题风格要多展示一些，我也想看看DaisyUI具体有哪些样式。Q5.2 移动端/手机适配：需要。”
> - **边界与特例逻辑**：
>   - 主题切换不能只是简单的下拉框，必须以画廊色块形式充分展现 DaisyUI 的丰富样式与设计美学；
>   - 移动端体验作为一等公民考虑，支持手机随时打开查看与启停。
